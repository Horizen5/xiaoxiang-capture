# 架构

## 一、为什么走 CDP，不走抓包代理

小程序的网络请求走 WMPF（WeChat Mini Program Framework）的内部通道，不是标准
HTTP 代理能看到的流量。项目早期试过 mitmproxy（`tools/mitm_*.py` 是留下的痕迹），
只能拿到 TLS 层密文，且要装证书。

换成另一条路：WMPF 本身就是 Chromium。只要把它内置的 DevTools 协议暴露出来，
就能在渲染进程里 `Runtime.evaluate`，直接挂钩 `wx.request` —— 拿到的是**已经解析好的
结构化响应**，不需要解密，也不需要证书。

`wmpfdebugger` 干的就是这件事：用 Frida 给 `WeChatAppEx.exe`（新版是 `flue.dll`）
打补丁，让它在 62000 端口开一个 CDP 服务。

## 二、三个进程的分工

```
┌─────────────────────────────────────────────────────────────┐
│ start_beta.py（前台，你双击的那个窗口）                        │
│   · 找 node / python                                        │
│   · spawn 三个子进程，CREATE_NO_WINDOW + SW_HIDE（不弹黑窗）     │
│   · 守护：每轮检查存活，挂了就重拉；代理重启后抓包自动重连         │
└───────────┬──────────────┬──────────────┬───────────────────┘
            ▼              ▼              ▼
    ┌──────────────┐ ┌───────────┐ ┌──────────────────┐
    │ wmpfdebugger │ │live_capture│ │ monitor_server   │
    │ node :62000  │ │  websocket │ │ http :8899       │
    └──────┬───────┘ └─────┬─────┘ └────────┬─────────┘
           │  CDP            │ 读盘（只读）    │
           ▼                 ▼                ▼
     WeChatAppEx        live_raw/        浏览器看到的看板
     渲染进程            live_imgs/
```

**为什么要拆成三个进程**：抓包进程一断（微信重启、代理崩），历史数据不能丢；
看板必须能脱离抓包独立活着。三者之间只通过**磁盘文件**通信，没有共享内存，
所以任何一个死掉，另外两个都能继续工作，重启后自动接上。

## 三、注入的 hook 做了什么

`live_capture.py` 里的 `HOOK` 常量是一段直接 `evaluate` 到小程序运行时的 JS（v6）：

1. **保存原始 `wx.request`**，包一层，不改行为
2. 响应回来后判断是不是分类列表接口（看 URL 里有没有 `skuList` / `categoryId`）
3. 是的话把整个响应体 `__P[key] = resp`，再由 Python 侧通过 CDP 轮询取走
4. 同时把「当前页面停在哪个一级/二级/三级」记到 `__CAT`

Python 侧每 1.5 秒取一次，有新内容就落盘、并把商品图排队下载。

### 风控相关的三个坑（都踩过）

| 现象 | 根因 | 现在的做法 |
|---|---|---|
| 开了自动模式十几秒就弹滑块验证 | 脚本一次把 `loadNextPage`、`loadNextPageDebounce`、`onReachBottom` 全调一遍，同一秒翻两三页 | 一次只调一个（优先 `loadNextPageDebounce`），并加 2.1 秒硬节流 |
| 切分类后立刻发不匹配的请求 | 在「为你推荐」页盲调 `activeThirdCategory` 等四个方法，参数靠猜，页面状态被搞乱 | 删掉盲调。自动模式只做真实滚动，换分类必须人点 |
| 调试通道本身就改变了环境 | `hook` 把 `RemoteDebugMode` 置 1，且是**进程级**开关；还往全局注入了 `__isAppServiceRemoteDebugMode__` 等三个变量 | v6 hook 会擦掉这三个全局；但 `RemoteDebugMode` 复位只能靠**重启微信进程** |

实测数据（613 次真实请求、600 个响应全 `code=0`）：正常节奏最快 1.67 秒/次，
60 秒最多 34 次。所以节流值定 **2.1 秒**（≈ 1.67 / 0.8，留 20% 余量）。

## 四、看板为什么是「复刻」而不是「列表」

小程序的分类页是三层结构：

```
顶部：一级分类横滑胶囊（蔬菜豆制品 / 肉禽蛋 / …）
左侧：该一级下的二级分类竖排（为你推荐 / 在家火锅 / … / 超低折扣）
顶部第二行：当前二级对应的三级标签（低价捡漏 / 限时秒杀）
右侧：商品卡片流
```

看板按同样的布局渲染，操作习惯完全一致，不用重新学。数据全部来自只读扫描
`live_raw/`，扫描结果有 3 层缓存（文件 mtime+size、分类树、整页快照 5 秒），
所以几千个文件也不会卡。

## 五、一键启动小程序的三条路

按「打扰程度」从低到高排：

1. **已经开着** → `SetForegroundWindow` 直接置前（0 打扰）
2. **有桌面快捷方式** → `os.startfile(lnk)`，微信自己写的启动参数，等于硬调用
3. **都没有** → UI 自动化：抢前台 → `Ctrl+F` → 输入 `xxcs` → `Enter` → 轮询窗口出现

第 3 条是兜底不是首选。PC 微信没有对外的小程序唤起协议（详见 README「已知限制」），
所以没有 `lnk` 时只能用这条路。实测全流程 2.85 秒，用户零操作。

> 想彻底摆脱 UI 自动化：在小程序窗口点右上角「…」→「添加到桌面」，
> 那个 `.lnk` 放进桌面或 `tools/` 目录，`launch_miniapp()` 会自动优先用它。

## 六、进程身份校验（`_pidutil.py`）

Windows 会复用 pid。只判断「pid 还活着」有两个后果：

- 上一轮启动器退出、pid 被别的程序捡走 → 下次双击误报「已经有一个在跑」，永久挡住启动
- 清理残留进程时按 pid 杀 → 可能 `TerminateProcess` 掉无辜程序

所以 pid 文件存三个字段：`pid:可执行文件名:创建时间(FILETIME)`。三者对上才算同一个进程。
老格式（只有 pid）只认 `python.exe` / `pythonw.exe`，其余一律当过期记录清掉。
